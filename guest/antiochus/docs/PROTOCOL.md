# Antiochus: профиль antiochus-score-4

## Независимость и происхождение

[исх.] Исходная база изучения — beta 3: `guest/tests/gl-features.c`, `guest/tests/vmxpack.c`, `tests/fp-kernels-jit.c`, `tests/vmx-integer-jit.c`, `tests/epicycle/fp.S`. Из них взяты направления проверок: независимый программный GL, точные FP-значения/состояние, упаковка и перестановка компонентов, зависимости накопителей и память. Код JIT, его интерпретатор и поправки эталона под поведение Tiger/libGLImage не включены в Antiochus.

[исх.] Собственные CPU-эталоны: побитовый CRC против табличного с контрольным вектором `123456789`; `qsort` против merge sort; целочисленные суммы против FP-матрицы; прямой DFT отдельных частот плюс энергия против FFT; точные целочисленные результаты потоков памяти и медиакернелов. Это разные алгоритмы проверки, но всё ещё один проверяемый компьютер: не независимое аппаратное доказательство правильности CPU.

[ист.] Документальная основа API и архитектуры:

- [NXP MPC7450 Family Reference Manual](https://www.nxp.com/docs/en/reference-manual/MPC7450UM.pdf): состояние и FP PowerPC выбранного семейства.
- [NXP AltiVec Programming Environments Manual](https://www.nxp.com/docs/en/reference-manual/ALTIVECPEM.pdf): saturation, permute, FP и VSCR.
- [Apple: выбор OpenGL renderer](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/OpenGL-MacProgGuide/opengl_pixelformats/opengl_pixelformats.html), [offscreen](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/OpenGL-MacProgGuide/opengl_offscreen/opengl_offscreen.html): CGL/pbuffer и независимый software renderer; при разработке сверены локальные заголовки SDK 10.4.0.
- [Khronos ARB_shader_objects](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_shader_objects.txt), [EXT_framebuffer_object](https://registry.khronos.org/OpenGL/extensions/EXT/EXT_framebuffer_object.txt), [ARB_texture_float](https://registry.khronos.org/OpenGL/extensions/ARB/ARB_texture_float.txt), [ATI_texture_float](https://registry.khronos.org/OpenGL/extensions/ATI/ATI_texture_float.txt): объявления и контракты дополнительных путей.
- [Khronos OpenGL Registry](https://registry.khronos.org/OpenGL/index_gl.php): остальные стандартные форматы и расширения; не реализация стороннего эмулятора.

[исх.] Древний SDK 10.4.0 не содержит нужных объявлений FBO. Они объявлены локально по спецификации и разрешаются через `dlsym` после проверки capability. Это позволяет собирать с имеющимся SDK, не создавая обязательной зависимости старта приложения от новых entry points. Отсутствие advertised extension означает `unsupported`; отсутствие необходимых функций при объявленной поддержке означает ошибку.

[исх.] `vmx-*` — исторические технические ID трёх media-задач. Они включены в CPU на обеих архитектурах: G3 исполняет скалярный вариант, G4 при наличии AltiVec — векторный. Данные и объём работы одинаковы; backend записан в результат. Нет отдельного облегчённого задания для Ptolemy или определённого renderer.

[исх.] FBO, fill и upload меняют содержимое между jobs, поэтому потерянное обновление не может всегда скрыться за правильным результатом первого кадра. GPU-job включает CPU/API submission и завершение GPU; это не измерение только shader ALU. Для upload также включена подготовка меняющихся байтов. Setup и проверки изображений находятся вне измеряемого интервала.

[исх.] Дополнительные тесты используют advertised capabilities, а не утверждение «все R300/R500 имеют одинаковый набор OpenGL». GLSL branch не доказывает физическое исполнение ветви именно аппаратным branch unit. MSAA проверяет наличие промежуточного покрытия и разумные площади; сравнение конкретных аппаратных sample positions пока отсутствует.

## Измерения базовых случаев draft 3

[исх.] Отдельный worker на каждый case. Один первый job записывается как `cold_seconds`, после уже выполненного setup; это не холодный старт всей ОС или shader compiler. Затем batch удваивается до 0,15 s или 65536 jobs. Размеры данных и сами jobs не меняются. Пять измеренных batches дают время на job; медиана вычисляется заново в приложении из всех пяти значений.

[исх.] После первого job, прогрева и каждого measured batch выполняется проверка правильности. GPU завершает работу через `glFinish` внутри измерения; `glReadPixels`, эталон и сохранение изображений находятся снаружи. Первый runtime/JIT прогрев и стоимость проверок сохраняют собственное влияние на cache state; это одинаковая часть метода, а не случайно забытая стоимость.

[оценка] В сравнительных сериях запускать одинаковые бинарники, одинаковую ОС и одинаковые параметры гостя. Для сравнения ОС явно отметить изменение. Сделать A/A, затем минимум несколько независимых ABBA по полным запускам; не смешивать profiler-сессию с timing. Пять внутренних batches не являются пятью независимыми загрузками. Разброс сообщается, но единичная разница не объявляется статистически значимой.

[исх.] Matrix-пара устанавливает FPSCR внутри job: преобразование таймера в double перед стартом не может незаметно превратить XX=0 в XX=1. Оба варианта имеют одинаковую математическую работу; стоимость установки состояния включена. Дополнительно записывается gettimeofday для каждого batch; расхождение гостевых часов свыше 5% при интервале от 20 ms отвергает результат. [оценка] Оба источника всё ещё принадлежат гостю: при приёмке нужно сверить длительность полной серии внешним таймером хоста.

## Базовая формула draft 3 и проверка старых изображений

[исх.] Для успешно проверенного обязательного подтеста: `q_i = 0.001 / median_seconds_i`. Для неуспешного: `q_i = 0`, независимо от показанной им скорости. Компонент считается по фиксированному числу обязательных заданий:

```text
component = 1000 * (exp(mean(log(1 + q_i))) - 1)
```

[оценка] Это геометрическое усреднение с добавленной единицей: отказ имеет определённый нулевой вклад, не исключается из знаменателя и не может получить бонус за сверхбыстрый неправильный вывод. При 1 ms/job во всех случаях компонент равен 1000. Нормировка условная и не калибрована по скорости Ptolemy, MHz CPU или эталонному Mac. Она не меняется после получения результатов без новой версии профиля.

[исх.] Двенадцать CPU-заданий и семь основных GPU-заданий имеют равные веса внутри своего компонента. Ошибка архитектурного CPU gate обнуляет CPU полностью. GPU core сохраняет все семь членов в знаменателе, включая нулевые за отказы. Затем GPU умножается на долю прошедших среди доступных дополнительных GPU-проверок (при отсутствии доступных дополнительных проверок множитель 1). Недоступные дополнительные возможности не штрафуются; изменение покрытия выявляет `compare.py`. Общая оценка — `sqrt(CPU*GPU)`.

[исх.] Отдельное поле `gpu_speed` применяет ту же формулу только к прошедшим основным GPU-тестам. Это индекс скорости данного поднабора, не всех возможностей GPU. Сравнивать его можно только при одинаковом прошедшем поднаборе и покрытии; `compare.py` проверяет это. `gpu_passed/gpu_checked` сообщает качество основных и доступных дополнительных проверок. Два диагностических теста не влияют на оценки; их ошибки сохраняются отдельно.

[оценка] Линейный штраф также является политикой качества, не физической моделью ущерба. Нельзя представлять рост score-3 относительно score-2 как ускорение Ptolemy. Сохраняются исходные времена и статусы; неверный быстрый результат не даёт баллов. Формула фиксируется до новых A/B-прогонов.

[исх.] Проверяются все RGBA-компоненты по тем же координатам: tolerance 1 для аналитических изображений, 3 для software-сравнения сложных сцен. Нет поиска «похожего пикселя рядом», поправок по имени игры/GPU или изменения ожидаемой картинки по фактическому выводу Ptolemy. Difference-image усиливает дельту ×4 с насыщением; `.rgba` сохраняет исходные значения alpha без потерь.

[неизв.] Строгость сравнения сложной геометрии ещё не откалибрована на независимом железе. Если расхождение укладывается в документированную свободу OpenGL, нужно уточнить сам общий тест/его область однозначности и повысить версию профиля, а не вводить исключение для Ptolemy. До этого профиль остаётся draft.

## Classic

[исх.] Classic измеряет CRC 64 KiB и QuickDraw: 32-bit GWorld 257×129, fill и CopyBits с проверкой всех RGB-пикселей вне timing. Дополнительно копирует результат в видимое окно, но обратного чтения видимого окна нет. Пять времён каждой задачи сохраняются отдельно. Это проверка конкретного QuickDraw-пути, не исчерпывающий тест всех Classic API или 3D.

[исх.] Результат принимается только для protocol `antiochus-classic-1` и nonce текущего запуска. Поздний результат другого запуска не переиспользуется. Входной документ адресуется через AppleEvent; ответ пишется рядом с ним через FSSpec, без предположения о совпадении OS 9 Desktop и OS X Desktop.

## Пределы покрытия

[неизв.] В эту версию не входят исчерпывающие VMX/FPSCR-векторы, SMP/барьерные litmus, полный register-level R300/R500 conformance, все compressed/float/cube/3D/mipmap форматы, recovery после host GPU hang и все Classic 3D API. Направленные тесты из beta 3 здесь дополнены независимыми прикладными нагрузками, а не объявлены полной заменой всей тестовой базы.

[оценка] Успешность релиза состоит из двух разных условий: приложение собирается/работает на заявленной матрице, а его проверки отличают ошибки от допустимых различий. Только второе позволяет использовать падение GPU-балла как доказательство регрессии графической корректности.

[исх.] Теперь фактическое наличие multisample storage проверяется до измерения; без него MSAA имеет статус unsupported. Профиль повышен до `antiochus-score-2`; отчёты draft 1 не ранжируются вместе с draft 2.

[ист.] Apple отдельно описывает ограничения сочетания pixel buffers и multisampling: [NSOpenGLPFAMultisample](https://developer.apple.com/documentation/appkit/nsopenglpfamultisample), [Scene Antialiasing](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/OpenGL-MacProgGuide/opengl_fsaa/opengl_fsaa.html). [исх.] Нулевое число samples не является доказательством неисправного MSAA аппаратуры: этот путь его не проверяет.

## Изменение draft 3

[исх.] Профиль содержит 29 native cases: gate, 12 CPU, 7 основных GPU, 7 дополнительных GPU, 2 диагностических. Старые нагрузки, графические эталоны и допуски сохранены. Новые случаи:

| Случай | Работа и роль |
|---|---|
| [исх.] `cpu-veclib-fft` | Настоящий Accelerate `vDSP_fft_zip`: 2048 complex float, forward, split complex, stride 1. Сброс входа включён во время, setup/DFT вне времени. 17 бинов против прямого double DFT, Parseval, конечность. CPU-компонент. |
| [исх.] `gpu-window` | Видимое окно 512×256, 5 серий по 60 кадров с меняющимся двоичным рисунком; целевой темп 60 Hz, swap interval 0. Дополнительная проверка GPU. |
| [исх.] `gpu-window-offscreen` | Та же геометрия и темп в pbuffer; диагностический контроль, без влияния на балл. |
| [исх.] `gpu-shader-branch-fallback` | Тот же шейдер, но без NoRecovery; диагностический контроль, не исправляет отказ основного случая и не доказывает аппаратное исполнение. |

[ист.] `vDSP_fft_zip` — in-place single-precision complex FFT: [Apple](https://developer.apple.com/documentation/accelerate/vdsp_fft_zip). [исх.] Тест не воспроизводит неизвестные нам размеры, подготовку и внутренний цикл Xbench; он добавляет прежде отсутствовавший вызов системной vecLib. Её выбор G3/G4-кернела остаётся за ОС.

[исх.] Экранный тест отдельно записывает draw+finish и swap+finish на кадр, сумму активного времени, wall duration и опоздания относительно 60 Hz. Паузы и проверки не входят в `sample_n`; это не FPS, не пропускная способность GPU и не момент физического scanout. После серии проверяются GL back buffer и прочитанная область дисплея с тем же номером кадра. Сохраняется только область тестового окна, а не весь рабочий стол. Выводится последняя проверенная серия либо первая ошибочная.

[исх.] Чтение дисплея использует документированный в SDK 10.4.0 `CGDisplayBaseAddress`, без эксклюзивного захвата дисплея. Поддерживается PPC big-endian xRGB32, основной дисплей с совпадающими Cocoa/pixel-размерами. Неподдерживаемый формат или невозможность чтения означают отказ проверки с причиной, не pass. Прямое чтение framebuffer не проверяет физический монитор или последнее отображение на host. Перекрытое окно, меню, уведомление или перемещение курсора внутрь рисунка могут нарушить проверку; окно следует оставлять открытым и свободным. Тест вызывает `UpdateSystemActivity(UsrActivity)` вне измерения, чтобы задержать сон/затемнение дисплея.

[оценка] Экранный worker запускать в активном графическом сеансе; для принятия использовать обычный запуск Antiochus. Минимизированный/спящий дисплей не является корректной средой для этого случая. Ни sleep, ни screenshot не доказывают завершение физического scanout. Метод проверяет наблюдаемую картинку в пяти контрольных точках, а не каждый из 300 кадров.

[исх.] Оба branch-случая теперь сохраняют результат отдельной очистки RGBA до первой нагрузки и статус линковки программы. Это позволяет отделить потерю alpha ещё на очистке от результата последующего рисования.

[исх.] `compare.py` сохраняет чтение старых score-2 отчётов, но запрещает смешанное ранжирование score-2/score-3. Пять внутренних серий не заменяют независимые A/A и ABBA.


## Draft 4: тематическое окно и совместная нагрузка

[исх.] Первые 29 случаев сохранены. Добавлены пять сцен в одном и том же видимом окне 768×432, без GLSL 1.20 и без обязательного MSAA. Используются ускоренный double-buffered OpenGL, fixed-function transforms, VBO, текстуры, depth, alpha blending; у камня также два направленных источника fixed-function освещения. Невозможность создать ускоренный контекст не скрывается программным fallback.

| Случай | Объём и содержание |
|---|---|
| [исх.] `gpu-rosetta` | 44 треугольника: вращающийся камень, текстура, свет, постамент. |
| [исх.] `gpu-paneion` | 20 496 треугольников: рельеф, вода, 320 деревьев. |
| [исх.] `gpu-phalanx` | 90 640 треугольников: 512 пехотинцев, 480 деревьев; более крупный план. |
| [исх.] `gpu-cavalry` | 251 472 треугольника: 1536 пехотинцев, 96 всадников, 640 деревьев, 192 пылевых элемента. |
| [исх.] `combined-panion` | 611 936 треугольников: 4312 движущихся агентов, 800 деревьев, 768 пылевых элементов. |

[исх.] В каждом случае — один прогревочный кадр, сброс сцены, затем пять серий по 48 кадров. На кадр приходятся два фиксированных шага симуляции; камера зависит от номера кадра. Быстрая машина не пропускает работу и не получает другую сцену. CPU пересчитывает движение, пространственный индекс, геометрию персонажей и порядок прозрачных треугольников; GPU выполняет преобразования и отрисовку. Число объектов и геометрия не адаптируются к FPS. Это не утверждение о 100-процентной загрузке обоих процессоров и не измерение GPU ALU отдельно.

[исх.] `frames.tsv` разделяет CPU simulation, submission, ожидание `glFinish`, presentation и сумму активного времени кадра. Синхронизация намеренно ограничивает перекрытие CPU/GPU. Итоговое время — медиана пяти средних активных времён. Запись журналов, обработка событий и проверки исключены. FPS в заголовке окна использует прошедшее реальное время; `fps_from_active_time` — обратная величина измеренного активного времени, другая метрика. Сравнивать их как одно число нельзя.

RGB-допуск 4. Пограничные участки исключаются симметрично изнутри и снаружи треугольника (0.25 пикселя), учитывается неоднозначность глубины в два шага 24-bit depth и близость границы texel. Нужно не менее 128 однозначных точек, а для сцен с войсками — дополнительно не менее восьми точек на их непрозрачной геометрии. Ожидаемый цвет не извлекается из проверяемого изображения. Это выбранный контракт draft, не гарантия одинаковой растеризации всех драйверов.

Эталон изображения использует геометрию самой сцены: он проверяет её отображение, но не доказывает правильность всей генерации модели или эмуляции PowerPC.

Полное RGB-различие дисплей/буфер записывается диагностически: преобразование цвета и особенности композиции ещё не откалиброваны. Поэтому возможна ситуация `pass` по эталону/номеру кадра при ненулевом диагностическом различии. Это не доказательство отсутствия всех экранных артефактов. ## Формула score-4

[исх.] CPU-компонент не изменён. GPU core содержит семь прежних случаев плюс четыре тематические сцены. Для прежних `q=0.001/t`, для сцен `q=(1/60)/t`; неправильный результат даёт `q=0`. Core равен `1000*(exp(mean(log(1+q)))-1)` с фиксированным знаменателем 11. Доступные дополнительные проверки и корректность финальной битвы дают линейный множитель доли успеха. Скорость финальной битвы не включается в GPU core.

[исх.] `combined=1000/(60*t_panion)` только при успешном результате и CPU gate; иначе ноль. `Overall=cbrt(CPU*GPU*combined)`. Поэтому провал финального совместного теста не может дать положительный Overall. В интерфейсе остаются CPU/GPU/Overall; отдельный combined хранится в отчёте. Константа 60 — выбранная нормировка, а не результат эталонного Mac.

[исх.] `compare.py` принимает score-2/3/4 по отдельности и запрещает ранжирование разных профилей. Переход на score-4 не является ускорением Ptolemy. Нужны повторные A/A и ABBA на одном бинарнике, при одинаковой конфигурации и свободном видимом окне. Единичный приёмочный запуск годится для проверки работоспособности, а не для заявления о росте скорости.
